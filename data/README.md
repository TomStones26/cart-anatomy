# 数据集说明

六张源表，共 59,000 条记录，均为 UTF-8 with BOM 编码的 CSV。

| 文件 | 行数 | 说明 |
| --- | ---: | --- |
| `orders.csv` | 15,000 | 订单主表。15 列，含订单状态、金额、发货/收货时间、评价 |
| `user_behaviors.csv` | 30,000 | 用户行为流水。四类行为（浏览/点击/收藏/加购） |
| `users.csv` | 5,000 | 用户属性。年龄、性别、省市、注册日期、会员等级、信用分 |
| `user_features.csv` | 5,000 | 用户聚合特征。累计消费、订单数、各行为次数、消费层级 |
| `products.csv` | 2,000 | 商品属性。名称、品类（15 类）、品牌（113 个）、价格 |
| `product_features.csv` | 2,000 | 商品聚合特征。销售额、销量、各行为次数、转化率、评分、热度分 |

## 需要注意的数据特征

这几条会直接影响分析口径，动手前建议先看：

1. **时间范围**：订单下单时间从 2025-09-06 到 2026-03-05，但 **2026-03 只有 5 天数据**（375 单，占全量 2.7%）。做月度趋势时末尾的下跌是数据边界，不能读成业绩下滑。
2. **时间戳带时分秒**：`order_date` / `delivery_date` 全部带 `22:38:35` 的时间部分，没有一条落在整点。与纯日期维度表建关系时按值精确匹配会**一条也匹配不上**，必须先派生出纯日期列。
3. **自然缺失 vs 异常缺失**：`delivery_date` 缺 3,731、`receive_date` 缺 5,942、`review_score` 缺 10,777、`review_content` 缺 11,461。这些**不是脏数据**，而是业务状态决定的——没发货就没有发货时间，没评价就没有评分。**不要填充**。
4. **未评分率 71.85%**：意味着"评分"字段不足以支撑满意度结论，需要改用行为数据。
5. **行为与订单不成比例**：加购行为仅 2,949 条，而有效订单有 13,946 笔。这不是一条真实的下单路径，漏斗只能用于横向比较品类，不能当绝对转化率。
6. **地域分布均匀**：20 个城市，前 15 名每城 242–272 人，极差仅 12%。条形图上几乎一样长是真实分布，不是图表错误。

## 数据来源

数据集取自公开的数据分析练习项目（Heywhale 平台「基于 SQL 与 Power BI 的淘宝消费数据分析与可视化」），用于学习与复现。原始数据未做任何修改，清洗仅在分析过程中通过字段映射、类型转换与口径定义完成，源文件保持原样。
